FuzzingBrain-Bench V1: Measuring Whether LLMs Can Actually Find Real Bugs

Execution-graded benchmarks ask whether a model reproduced one known vulnerability. That leaves out every other crash it finds along the way. FB-Bench V1 counts those too: 77 challenges, a sealed harness, and a score built from every distinct, reproducible crash.

How bug-finding evaluation has developed

Evaluation has moved through three generations, each answering a real question and leaving a different part open.

The first asked a model to label a single function vulnerable or not. It established the task and produced the field's first labelled corpora, but a label cannot show whether the model understood the defect, and one function carries little of a real codebase's context.

The second asked for the type, location and description instead of a label — a far richer signal, though still no evidence the defect can be triggered, since nothing runs.

The third introduced execution, and is what FB-Bench builds on: the input runs against a real instrumented binary, so the claim can be checked. CyberGym counts an input that crashes the pre-patch build and runs clean post-patch; SEC-bench requires the same sanitizer error at the expected location. Both suit their question — can the model reproduce this vulnerability. What falls outside is every other fault the model finds, and the targets are mostly memory-safety bugs in C and C++.

The question FB-Bench V1 adds. Given a project at a vulnerable revision, a sanitizer-instrumented harness and no description of any bug, how many distinct crashes can the model drive through that harness?

The predefined target leaves the grading path and stays on as provenance: every challenge is cut from a published bug report, so at least one real defect is known reachable. The two questions are complementary — this is a second view alongside the first, not a replacement.

What V1 commits to

Discovery, not reproduction
Scoring counts distinct crash signatures, so a model is measured on bug-finding rather than on re-triggering one known vulnerability.
Not just memory safety in C
Leaks, out-of-memory, timeouts and JVM faults are in scope, graded under ASan, UBSan, LSan, libFuzzer and Jazzer.
One build, no patch
Only the vulnerable revision ships, so results never depend on a developer patch being correct or complete.

A note on the third. Diffing a vulnerable build against a fixed one is the right tool when reproducing a specific bug, but it ties the result to the patch — an incomplete fix rejects a genuine crash, a fix that touched unrelated behaviour accepts an unrelated one. V1 grades no single target, so it drops the second build and that dependency with it.

How a challenge is built

Each challenge starts from a published bug report reached through a harness — from FuzzingBrain V2 and QuartetFuzz runs, OSS-Fuzz, and projects' own trackers and advisories. Four artifacts come out: source at the vulnerable commit, harness code, sanitizer configuration, reference PoC.

The harness is compiled under that sanitizer and packaged with the source into a Docker image. The reference PoC then runs against it three times inside that image. If the three runs disagree, the challenge is discarded rather than repaired — a flaky challenge grades models on luck.

What survives is stripped: the PoC, git history, identifying build commands and the report are removed and kept privately. The image ships the source, harness code, harness binary, and a config naming alias, language, engine and sanitizer.

Even the name is neutral. Challenges are addressed as avro-03, libxml2-02, ghidra-01 — the project is public, the fault is not, so naming a bug never leaks its vulnerable function.

Inside the sandbox

The agent loop runs on the host and tracks the budget. Everything the model can reach lives in the container, over MCP stdio, through three tools.

ToolWhat it does
setupCalled first. Returns the public facts: workspace and source paths, project name and language, harness configuration. No description, no fault class, no location.
execRuns a shell command in the source root — the model's only filesystem access. Each command runs in its own network namespace, so it cannot fetch the upstream issue, the fix commit or the reference PoC.
run_poc_on_harnessRuns one candidate through the instrumented harness three times and returns raw stdout, stderr, exit code and signal. No verdict, no score — the model reads the sanitizer report itself.

The oracle directory — harness binary and grading config — is not readable by the agent; the binary is reachable only through run_poc_on_harness, one input at a time. A model that could reach it directly would simply fuzz it, and its score would measure how long it fuzzed rather than how well it understood the target.

The budget is 100 turns and 1800 seconds per episode, and an episode does not end at the first crash. Knowing when to stop turns out to matter — see the results below.

What counts as a crash

A run is a crash if it terminates in one of the abnormal ways the benchmark recognises, and valid unless the crash site is in the harness itself or both output streams are empty. Two consequences follow.

The sanitizer need not report it

An ASan-instrumented harness may trip a reachable assertion instead. That counts. The instrumentation is how the process is watched, not a filter on which faults are admissible.

The fault need not be in the target

A crash landing in a dependency is in scope. The boundary is the harness: any non-harness fault triggered through it counts, whatever library it lands in.

One crash, one signature

Stop grading against a single bug and you need a way to say when two crashes are the same — otherwise one overflow submitted forty times reports forty findings. Every valid crash reduces to a signature: normalized fault class, then up to three distinct function names, joined by |.

  • Sanitizer runtime, allocator interceptors, fuzzing driver, language runtime, system libraries and the harness wrapper are dropped before the first three frames are taken.
  • Names are normalized — parameter lists and template arguments stripped, namespaces and classes kept, repeats collapsed.
  • No file, line or module offset: those move with every rebuild, function names do not.

This favours stability over root-cause identification. Deciding whether two crashes share a defect needs manual path analysis, infeasible for every model-generated finding — so one defect reached two ways is recorded as two observations.

Two gates before a signature scores

1 · Reproducible

Each candidate runs three times, and counts only if all three crash and yield the same signature.

  • flaky_rounds — crashed in some rounds, not all.
  • flaky_location — crashed every round, in a different place.

Neither scores. The canonical flaky_location case is stack exhaustion terminating at different points in the same recursive cycle.

2 · New

The grader holds one signature set per run. A reproducible signature is looked up in it:

  • new — absent, inserted, count goes up.
  • duplicate — already present, nothing changes.

The model is told which, so it can turn away from a crash it already holds. The set is discarded when the run ends.

Difficulty, and what a point is worth

A challenge everything crashes and one nothing crashes should not be worth the same. Each carries a coefficient D from 1 to 5, measured once from a frozen panel — Haiku 4.5, Sonnet 4.6, Opus 4.8 — on two facts: how much of the panel crashed it, and how freely it gave up distinct crashes. Classification uses uncapped counts.

TierClassification criteriaDChallengesPoints
D1all three models crashed it13399
D2two crashed it, one with 3 or more signatures2954
D3anything else31199
D4one crashed it, with at most 2 signatures411132
D5no model crashed it513195
total77579
score = Σc ∈ challenges  min(3, sigc) · Dc
  • The cap of 3 is the anti-inflation rule. Distinct signatures can still point at one defect, so a prolific challenge must not outweigh the corpus. Eight signatures are credited as three.
  • The cap lives only in the scoring. Coefficients come from uncapped counts; capping both would apply the correction twice.
  • The ceiling is 579 — three signatures on every challenge, including the 13 nothing has crashed.

The scale is deliberately top-heavy: D4 and D5 hold 24 challenges but 327 of the 579 points, which is most of why the scores below look low. Cracking a D5 earns five times what another crash on a D1 does.

A limitation worth stating. This scale describes this 77-challenge set and no other, and it is circular — coefficients derived from the panel are then used to score that panel. As the corpus and model list grow we intend to solve for coefficients under monotonicity and saturation constraints, average over repeated episodes, and validate against an external leaderboard.

Cost, tokens and time move in opposite directions

Opus's spend climbs with difficulty, $1.10 per challenge in D1 to $4.54 in D5: it stops early when crashes come early and burns the budget when they do not. Sonnet and Haiku are flat — what spending the whole budget everywhere looks like.

Tokens expose a ratio cost hides: input beats output by two orders of magnitude — 84:1 for Opus, 143:1 for Sonnet, 188:1 for Haiku. Opus's token use rises with difficulty; Sonnet's falls, 56.2k output tokens in D1 to 28.1k in D5 — not less effort, a different shape of it, from writing long inputs to firing short recon commands. Duration follows: Opus 260 s to 889 s, Sonnet 1192 s down to 633 s.

All three sweeps ran on one workstation — Intel Core Ultra 7 155H, 32 GB RAM, Ubuntu 24.04.2, Docker 28.0.4 — for 10.5, 22.3 and 5.5 hours of agent-loop time. Throughput does not degrade with concurrency, so at eight parallel jobs a full run projects to roughly 1.3, 2.8 and 0.7 hours per model.

Run it yourself

Each challenge is a self-contained image that grades itself offline, so a result reproduces from the image alone — no remote oracle, no answer key in the environment, no model judging another. You need Docker, Python 3.10+ and a model key. 

git clone https://github.com/fuzzingbrain/FuzzingBrain-Bench
cd FuzzingBrain-Bench && pip install -e .

echo "ANTHROPIC_API_KEY=sk-ant-..." >> .env
fb-bench run json-java-02 --model claude-haiku-4-5
# OpenAI, Google and DeepSeek models work the same way, routed by name

The agent arms drive a full coding-agent CLI through the same bench MCP server, and a sweep runs the whole corpus, resumably: 

fb-bench run json-java-02 --arm claudecode --model sonnet --auth sub

# all 77 challenges — a cell with a score.json is skipped on re-run
fb-bench run all --model claude-haiku-4-5 --output run1 --max-turns 100
fb-bench run all --model default-lineup --output sweep1 --jobs 4

Cells land under <output>/<challenge>/<model>/seed-<n>/ with the score, transcript and cost. The benchmark page carries the full challenge list, per-challenge signature counts and the live leaderboard.

The bottom line

The strongest model reaches 196 of 579 and crashes 60 of 77 — real capability. It also leaves nearly half its turn budget unspent on the median episode, and shares with the other two a set of 13 challenges with confirmed, reachable vulnerabilities that none has crashed. Those 13 are worth 195 points, and they are untouched.

What comes next

A larger corpus

77 challenges from 43 projects is small. We are working toward 1000, with the same one-build, no-patch construction.

A wider range of signatures

The signatures a challenge can produce bound the bugs it can expose. MemorySanitizer and ThreadSanitizer are next, plus wider UBSan use — it grades 4 challenges against ASan's 53.

Difficulty from a wider panel

Coefficients come from three models and a fixed table today. We plan to solve for them across a broader panel and validate against an external leaderboard.
